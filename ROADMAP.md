# Roadmap

Inventory targets one Active Directory domain, fewer than 500 Windows computers and a small IT team. This roadmap closes the gaps that cost such a team time every day when compared to comparable inventory and deployment products, in this order of impact: robust deployment, multi-user and permissions, deeper inventory, reporting and alerts. Everything that only pays off above this scale stays out ([see the end](#explicitly-out-of-scope-simple-by-design)).

Each item is tracked as a GitHub issue in the milestones [v0.2](https://github.com/erSitzt/inventory/milestone/1), [v0.3](https://github.com/erSitzt/inventory/milestone/2) and [v0.4](https://github.com/erSitzt/inventory/milestone/3). Order within a release is not a commitment; items may move between releases as they are refined.

**Legend:** **[DB]** = database migration · **[Runner]** = change to the runner on the target computers (agents pick it up through the existing self-update) · Effort: S = 1–2, M = 3–5, L = 6–10, XL = more than 10 person-days, including tests and English/German strings.

## v0.2 – Deployment robustness and roles

*Deployments survive reboots and offline targets, know whether software is already installed, stop themselves when they go wrong and respect maintenance windows; helpdesk staff can use the tool without being administrators.* (≈ 30–40 person-days)

| # | Item | Why it matters | Approach | Decisions / risks | Effort |
|---|---|---|---|---|---|
| 2.1 [#1](https://github.com/erSitzt/inventory/issues/1) | **Reboot and resume** [DB] [Runner] | A `Reboot` step ends the job; steps after it and the final scan are skipped. Drivers, runtimes, feature updates and "uninstall A, reboot, install B" chains cannot be done in one package. | Server-side continuation that works for all three transports: `DeploymentService.RunTargetAsync` detects a succeeded Reboot step in the `JobResult`, stores `ResumeFromStep` on the `DeploymentTarget` and sets a new `TargetStatus.WaitingReboot`. `RetryWaitingAsync` (already a 5-minute tick) probes until the host answers with a newer boot time, then ships a manifest with the remaining steps. The runner marks the remaining steps as `Deferred` (new `StepStatus`) instead of skipping them. `MarkInterruptedAsync` preserves `WaitingReboot` like `WaitingOffline`. | One persistent step list, no second manifest format. Reboot wait timeout (default 30 min, setting) → Failed. Agent-local resume is a later optimisation. | M |
| 2.2 [#2](https://github.com/erSitzt/inventory/issues/2) | **Detection rules and post-install verification** [DB] [Runner] | Re-running a package on a collection reinstalls, reboots or fails (MSI 1638) on computers that already have it; the exit code is the only proof of success. | `Package.Detection` reuses `StepConditions` and `ConditionEvaluator`, plus two new condition kinds: `SoftwareInstalled` (display name, optional minimum version, read from the Uninstall keys like `InventoryCollector`) and `MsiProductCode`. The runner evaluates detection at job start → new target status `AlreadyInstalled`; with the package flag "verify after install" it evaluates again after the last step → `Failed("verification failed")`. Package editor offers "fill from MSI"; library packages are prefilled from the catalog. | Optional – packages without detection behave as today. Dashboard shows "succeeded" and "already installed" separately. | M |
| 2.3 [#3](https://github.com/erSitzt/inventory/issues/3) | **Uninstall step and "Uninstall" from the software overview** [Runner] | Removing unwanted software (old Java, unapproved tools) is as common as installing; today it needs a hand-written command per product. | `StepType.Uninstall` with a display-name pattern or MSI product code. The runner resolves the `UninstallString` from the registry (HKLM both views, HKU for per-user installs), uses `msiexec /x {code} /qn /norestart` for MSI and the existing silent-switch table for EXE uninstallers; success codes 0/3010/1641. The software overview gets "Uninstall on these computers", which builds an ad-hoc one-step package. Library packages can generate an uninstall counterpart on demand. | EXE uninstallers without a known silent switch fail with a clear hint rather than guessing. | M |
| 2.4 [#4](https://github.com/erSitzt/inventory/issues/4) | **Maintenance windows** [DB] | Pushing a reboot package at 10:00 onto a sales floor is the classic self-inflicted outage; comparable products all have maintenance windows. | `Collection` gets an optional maintenance window (days-of-week bitmask, from/to local time – reusing the `Schedule.DaysOfWeek` semantics and `ScheduleCalculator`) plus a global default window in settings. `Deployment` and `Schedule` get `RespectMaintenanceWindow`. A target outside its window is parked as `TargetStatus.WaitingWindow` and picked up by `RetryWaitingAsync` within the existing `RetryUntilUtc` deadline. A computer's window is the union of the windows of its collections, else the global default. Ad-hoc "Run command" ignores windows. | Union, not intersection (the operator wants "allowed somewhere"; the UI shows which window applied). No per-computer windows. | S–M |
| 2.5 [#5](https://github.com/erSitzt/inventory/issues/5) | **Per-step retries, disk-space pre-check, close processes** [Runner] | Installers fail transiently (MSI 1618 "another installation in progress", file in use, network hiccup); a full disk fails late; "close Outlook first" is a daily requirement. | `JobStep.Retries` and `RetryDelaySeconds` (runner loop around the step; retry only on Failed, not on Skipped; MSI 1618 gets a default of 3 × 60 s). `StepConditions.MinFreeDiskMb` on the system drive plus an automatic pre-check for Install steps (2 × package size). `JobStep.CloseProcesses` (image names the runner terminates before the step, with an optional prompt in the user session when someone is logged on). | No user deferral yet – that needs state across jobs (backlog). | S–M |
| 2.6 [#6](https://github.com/erSitzt/inventory/issues/6) | **Failure threshold and per-deployment parallelism** [DB] | A broken package rolled out to 300 machines by a schedule at night is the worst case; today nothing stops it. | `Deployment.MaxFailures` (absolute or percent), evaluated when a target finishes: when exceeded, cancel the deployment and mark queued targets `Cancelled("stopped after N failures")`. Expose `MaxParallelTargets` (today a constant of 16) as a global setting with a per-deployment override; the first targets act as an implicit pilot because queued targets only start when slots free up. Schedules inherit the threshold. | Default for scheduled deployments: 10 % after at least 5 targets. | S |
| 2.7 [#7](https://github.com/erSitzt/inventory/issues/7) | **Roles: Admin, Operator, Viewer** [DB] | A helpdesk colleague should look up computers and run approved packages, but not edit credentials, settings or packages – which run as SYSTEM everywhere and are therefore domain-admin-equivalent. Today one allowed group means full admin. | Configuration `Inventory:Roles:{Admin,Operator,Viewer}` with groups for Windows (SID or name) and OIDC (group claims or app roles); the existing `AllowedGroups` maps to Admin for compatibility. Roles are resolved once at sign-in (`AccessControl.SessionPrincipal` and the Negotiate path) into role claims; three authorization policies next to the existing fallback policy; pages and mutating buttons use `AuthorizeView` with roles, minimal API endpoints `.RequireAuthorization(...)`; defence in depth through a guard in `DeploymentService.StartAsync` and package mutations via an injected current-user abstraction. `ApiToken.Role` – a token never exceeds its creator's role. Agent endpoints are unaffected. | Operator = view everything, run scans, deploy approved packages, cancel/retry, use remote access. Viewer = read only. No per-collection scoping (backlog). | M–L |
| 2.8 [#8](https://github.com/erSitzt/inventory/issues/8) | **Package approval flag** [DB] | Separates "someone is editing this" from "safe to deploy" without a workflow engine. | `Package.ApprovedBy` / `ApprovedUtc`. Any edit (steps, files, library auto-update) clears the approval unless an Admin ticks "keep approval". Operators only see approved packages in deploy dialogs; schedules refuse to fire unapproved packages and show a warning. | Setting "auto-approve library updates", default off. | S |
| 2.9 [#9](https://github.com/erSitzt/inventory/issues/9) | **Audit completeness, retention and export** [DB] | Incident reviews ask "who signed in" and "who changed the collection that this schedule targets". Sign-in/out, collection changes and package creation are not logged today, and the log never shrinks. | Log sign-in, sign-out and denied attempts (OIDC token validation, `/login/windows`, `/logout`), collection create/edit/delete, package create/rename/approve; store the actor's role and the token used. Retention setting (default 730 days, cleaned in the same daily tick as the change history). CSV export and filters by user/action on the Audit page. | The free-text `Action` stays; `AuditLinkMap` keeps turning names into links. | S |
| 2.10 [#30](https://github.com/erSitzt/inventory/issues/30) | **Fewer false alarms from endpoint protection (EDR)** [Runner] | Endpoint detection products rate the agentless SMB transport as lateral movement (file copied to ADMIN$, remotely created service with a new name, PowerShell with an execution-policy override). Every scan and deployment raises alerts, and with a few hundred computers real incidents get lost in them. | Authenticode-sign runner, agent and launcher in the release pipeline (shared with 3.9). Give the SMB transport a stable footprint: install the runner once under a fixed path and service name and hand jobs over through the job directory, instead of a new file and a new service per job. Make the agent – which only polls outbound – the recommended transport with a one-click rollout per collection. Avoid alert-prone PowerShell invocation patterns where possible. README section with narrow allow rules for Microsoft Defender for Endpoint (indicator by certificate, suppression scoped to server and runner path). | Suppression must stay narrow – a blanket exclusion for remote service creation would hide real attacks. A code-signing certificate costs money and needs safe storage; without it only the footprint, agent and documentation measures apply. | M |

## v0.3 – Inventory depth and compliance

*The inventory answers hardware, security-posture, patch and asset questions; collections and schedules act on them; required deployments keep new machines compliant automatically.* (≈ 35–45 person-days)

| # | Item | Why it matters | Approach | Decisions / risks | Effort |
|---|---|---|---|---|---|
| 3.1 [#10](https://github.com/erSitzt/inventory/issues/10) | **Hardware and platform security facts** [DB] [Runner] | Audits and upgrade planning need chassis type (laptop/desktop), UEFI and Secure Boot, TPM version/readiness, BitLocker per volume, GPU, RAM modules and free slots, physical disks (model, serial, SSD/HDD, health), battery health, BIOS date, monitors (manufacturer/model/serial from EDID) and printers. | New `InventoryCollector` sections, each wrapped in `Section(...)` so a failure only produces a warning: Win32_SystemEnclosure, firmware type and Secure Boot from the registry, Win32_Tpm, Win32_EncryptableVolume, Win32_VideoController, Win32_PhysicalMemory, MSFT_PhysicalDisk, Win32_Battery, WmiMonitorID, Win32_Printer. `InventoryData.Hardware` as a nullable sub-object (old agents keep working); scalar columns on `Computer`, child tables for memory modules, physical disks, monitors, printers and volume encryption; `InventoryDiff` and the CSV export extended. | Only classes available on Windows 10/11 and Server 2016+ without extra modules; everything optional. Scan time +2–5 s. | L |
| 3.2 [#11](https://github.com/erSitzt/inventory/issues/11) | **OS security posture** [DB] [Runner] | The security collections cover firewall, antivirus and updates. Missing: RDP enabled and NLA, UAC level, SMBv1, Credential Guard / LSA protection, built-in Administrator enabled and password age (LAPS check), Windows activation status, last logon of local accounts. | Registry/WMI/Win32 reads into a new `SecurityStatus.Posture` block; columns on `Computer`; one `RuleField` per fact so collections and alerts can use them. | Nothing that needs PowerShell modules on the target – registry/WMI/Win32 only, so it also works via WinRM. | M |
| 3.3 [#12](https://github.com/erSitzt/inventory/issues/12) | **Pending-update details and patch compliance report** [DB] [Runner] | "Which machines are missing this month's cumulative update?" is the most common compliance question; today only pending titles exist. | Extend the existing offline Windows Update search to return KB IDs, title, classification, MSRC severity, download state and size → table `ComputerPendingUpdate`. New report "Patch compliance": per computer (pending security/critical count, days since last install, reboot pending, WSUS vs Microsoft Update) and per KB (how many computers are missing it, drill-down → deploy). `RuleField.PendingSecurityUpdates`, `HotfixInstalled` / `HotfixMissing` (KB id). | Keep the 90 s timeout; cap at 200 pending items. | M |
| 3.4 [#13](https://github.com/erSitzt/inventory/issues/13) | **Windows Update step** [Runner] | Comparable products can trigger "install pending updates now" inside a maintenance window; without it patching remains a separate tool. | `StepType.WindowsUpdate` with options (security/critical only, include drivers, maximum count). The runner uses the Windows Update Agent COM API under SYSTEM (search, download, install), reports each update as output and sets exit code 3010 when a reboot is required so the Reboot step and the WaitingReboot flow (2.1) take over. Default timeout 2 h; WSUS or Microsoft Update as configured on the client. | Not available for run-as-user over WinRM (documented). No update approval catalogue – WSUS does that. | M–L |
| 3.5 [#14](https://github.com/erSitzt/inventory/issues/14) | **Active Directory OU, description and groups** [DB] | Most small domains structure computers by OU (Laptops / Desktops / Site A); collections should be able to say "OU contains Laptops" or "member of AD group X". | `LdapDirectorySource` additionally reads distinguishedName, memberOf, whenCreated, lastLogonTimestamp and operatingSystemVersion; `AdSyncService` stores the OU path, direct group memberships and the last AD logon. New rule fields `DirectoryOu`, `DirectoryGroup`, `DaysSinceDirectoryLogon`. Optionally restrict the sync to selected OUs. | Direct membership only (good enough); no write-back to AD. | S–M |
| 3.6 [#15](https://github.com/erSitzt/inventory/issues/15) | **Asset fields, tags and primary user** [DB] [Runner] | Who has the device, where is it, when does the warranty end – without that the tool cannot replace the spreadsheet every small IT team keeps. | Fixed columns on `Computer`: location, owner, cost centre, purchase date, warranty until, inventory number, notes, tags (chip UI). Editable on the computer page, importable via CSV (name → fields) and via API. The runner collects user profiles with last-use time → `ComputerUserProfile`; `Computer.PrimaryUser` = most-used profile of the last 30 days. Rule fields Tag, Location, WarrantyExpiresInDays, PrimaryUser; dashboard counter "warranty expires within 90 days". | Fixed columns instead of generic custom fields: they cover 90 % and keep collections and exports simple. Generic custom fields stay in the backlog. | M |
| 3.7 [#16](https://github.com/erSitzt/inventory/issues/16) | **Collection engine extensions**  | Rules exist but cannot express common sets (free disk space, uptime, service state, subnet, agent presence, nested collections). | New rule fields for 3.1–3.6 plus Domain, SerialNumber, CpuName, OsArchitecture, IpAddress (StartsWith = subnet), DiskFreeGb, DaysSinceBoot, ScanAgeDays, AgentPresent, ServiceState (name / Running|Stopped) and InCollection (collection-in-collection, cycle check, depth 3). `CollectionService` only loads the child tables a rule set references. | Flat AND/OR stays; collection-in-collection provides grouping cheaply. Wildcard `*` instead of regular expressions. | M |
| 3.8 [#17](https://github.com/erSitzt/inventory/issues/17) | **Required deployments (assignments) and richer schedule triggers** [DB] | "Every new computer in *Laptops* gets the baseline package" and "patch Tuesday + 3 days at 19:00" are the schedules operators actually want; monthly triggers and catch-up of missed runs are missing too. | `ScheduleTrigger.Monthly` (day of month or nth weekday, with offset days), `Schedule.EndLocal`, `Schedule.CatchUpMissed` (fire once if the last due time was missed by less than 24 h). New `ScheduleTrigger.OnMembership`: on each tick the scheduler computes the collection members minus the computers that already have a succeeded or already-installed target for this schedule (`Deployment.ScheduleId`) and starts a deployment for the remainder – rate-limited, respecting windows, retry-offline on by default. Per-schedule compliance "n of m members done". | Membership evaluation on the tick replaces event triggers and covers both AD sync and scans. Re-deploy at most once per 7 days when detection says the software was removed. | M |
| 3.9 [#18](https://github.com/erSitzt/inventory/issues/18) | **Signed self-update**  | Public repository, unsigned release download executed by the server: a supply-chain risk that reaches every managed computer through the agents. | Sign release assets with a maintainer key (Authenticode or minisign/ed25519); `UpdateService` verifies before staging; public key embedded in the build, rotation via appsettings; documented in SECURITY.md. | Fail closed; manual override setting for air-gapped mirrors. | S |

## v0.4 – Reporting, alerting and scale

*Problems reach the team by mail or chat before users call, monthly reports go out on their own, and night-time patching wakes machines up and rolls out in phases.* (≈ 30–40 person-days)

| # | Item | Why it matters | Approach | Decisions / risks | Effort |
|---|---|---|---|---|---|
| 4.1 [#19](https://github.com/erSitzt/inventory/issues/19) | **Notification channels: e-mail and webhook**  | Nobody watches a dashboard; failures must arrive where the team already is – mailbox, Teams or Slack channel. | A `NotificationService` with two providers: SMTP (host, port, TLS, credential via the existing `Credential` entity) and a generic webhook (POST JSON with presets for Teams adaptive cards and Slack blocks). Test button in the settings. Everything below sends through it. | No per-user preferences; one recipient list per rule. | M |
| 4.2 [#20](https://github.com/erSitzt/inventory/issues/20) | **Alert rules** [DB] | "Tell me when a computer loses its antivirus", "when a deployment finishes with failures", "when the AD sync fails", "when a machine returns that was missing for 60 days". | `AlertRule` table: kind CollectionEntered / CollectionCount (collection, threshold, cooldown) or SystemEvent (deployment finished with failures, schedule failed, AD sync / backup / self-update failed, agents outdated > N, scan errors > N, new computer discovered). `AlertState` keeps the last member set and last fired time so only deltas are sent. Evaluated in `SchedulerWorker` every 5 minutes; services raise system events through a small sink interface. Optional daily digest. | Dynamic collections are the rule language – no second expression system. | M–L |
| 4.3 [#21](https://github.com/erSitzt/inventory/issues/21) | **Saved reports, Excel export and scheduled report mail** [DB] | Management wants the same list every month; today it is a manual CSV export. | `Report` table: name, source (computers, software, patch compliance, deployments, changes), collection filter, column selection, sort. Export as CSV and XLSX (ClosedXML). Rendering goes through `ReportService` so the UI and the export share one query path. `ScheduleAction.Report` sends it via 4.1. | No PDF (print CSS on the report page is enough) and no custom report designer. | M |
| 4.4 [#22](https://github.com/erSitzt/inventory/issues/22) | **Dashboard charts and trends** [DB] | Counters without history do not show whether things are improving. | A nightly `DailySnapshot` row (computers, online, scanned, firewall off, antivirus problems, pending updates, reboot required, BitLocker off, warranty expiring, deployment success rate) written in the backup tick; MudBlazor charts: OS/release donut, 30-day trend lines, deployment success per week, scan-age histogram. | Aggregates only – the change history covers per-computer detail. | S–M |
| 4.5 [#23](https://github.com/erSitzt/inventory/issues/23) | **Software licence counting** [DB] | Small teams track licences in a spreadsheet while the software overview already knows the install counts. | `SoftwareLicense` table: name pattern (same matching as the Software rule field), licences owned, note, optional cost. The software overview shows owned vs installed with an over-/under-licensed indicator; alert kind LicenseExceeded. | No usage metering (backlog). | S |
| 4.6 [#24](https://github.com/erSitzt/inventory/issues/24) | **Wake-on-LAN** [DB] | Night-time patching fails because a share of desktops is powered off; WaitingOffline then waits for up to three days. | MAC addresses already exist in the network adapter table. A `WakeService` sends magic packets (UDP 9, subnet broadcast of the last known IP and directed) from the server; `RetryWaitingAsync` wakes WaitingOffline / WaitingWindow targets and probes again two minutes later; `Schedule.WakeTargets` and a "Wake" button on the computer page; `Computer.WakeMac` (first physical adapter). | Routed VLANs are reached through an agent in the target subnet (relay) or need directed broadcast; laptops on Wi-Fi rarely wake – documented. | S–M |
| 4.7 [#25](https://github.com/erSitzt/inventory/issues/25) | **Phased rollout** [DB] | For bigger changes (Office version, feature update) even a small team wants "pilot group first, the rest after two days if everything is fine". | Deployment options pilot collection, hold hours and maximum pilot failure percentage: phase 1 runs on the targets that are members of the pilot collection; phase 2 is created automatically for the remaining targets when the hold expires and the failure rate is below the threshold, otherwise the deployment stops and raises an alert. Builds on the failure threshold (2.6). | No more than two phases. | S–M |
| 4.8 [#26](https://github.com/erSitzt/inventory/issues/26) | **Operations and scale hygiene**  | Deployments and audit entries grow without bounds, the backup leaves out keys and the package repository, probes rely on TCP only, and the API is read-mostly. | Retention settings for deployments and audit (daily cleanup); backup includes the Data Protection keys and a zip of the repository (or a documented exclusion with a warning in the UI); optional ICMP pre-probe; API create/update/delete for packages (steps and file upload), collections, schedules and credentials (Admin only); bulk CSV import of computers with asset fields; parallelism settings exposed; `PRAGMA optimize` / `VACUUM` after cleanup. | SQLite stays – it is ample for 500 computers. | M |

## Backlog (after v0.4)

Collected in issue [#27](https://github.com/erSitzt/inventory/issues/27).

**Inventory**

- Generic custom fields (definitions in settings, values in a key/value table, available in collections and exports).
- Startup items, scheduled tasks, shares, certificates near expiry, Wi-Fi profiles, driver versions – each a small runner + schema item, added on demand to limit scan time and noise in the change history.
- Software usage metering (process start counts via the agent) for licence reclamation.
- LAPS integration: read the managed local administrator password as a credential source for agentless access.
- Software from offline user hives (today only loaded profiles).

**Platform**

- OIDC role mapping via app roles only, for tenants that cannot emit group claims.
- SQL Server / PostgreSQL provider – only if an installation outgrows SQLite.
- CVE mapping of installed software versions (false-positive heavy without CPE data); the "… outdated" collections from the package library already cover the practical case.

## Explicitly out of scope ("simple by design")

| Item | Reason |
|---|---|
| Distribution points, peer caching, BITS / bandwidth throttling | Fewer than 500 computers on a LAN; copying the package per job over SMB or HTTP is fine. Very large payloads can use a UNC-share step (backlog). |
| Multi-site relays / cloud gateway | One domain and one site is the target; VPN-connected laptops are served by the agent. |
| Two-person approval workflows | The package approval flag (2.8) plus the audit log is proportionate for a small team. |
| Full inventory snapshots per scan | The change history (730 days) answers "what changed when"; snapshots would multiply the database for no everyday benefit. |
| Custom report designer, PDF rendering | Saved reports with column selection, CSV/XLSX and the browser's print function cover the need. |
| OS deployment / imaging, driver management, Intune co-management | A different product category. |
| Built-in remote control | The launcher integrates Remote Assistance, Remote Desktop and shadowing; TeamViewer and AnyDesk are linked. |
| Linux / macOS clients | Windows-only inventory and deployment is the product definition. |
| Fine-grained API scopes | The token role (2.7) is enough; scopes add UI complexity without anyone asking for them. |

## Cross-cutting notes for implementation

- **Runner compatibility:** new inventory sections are nullable sub-objects or lists; the server treats null as "not collected by this runner version" (existing pattern). New step types fail with a clear message on old agents until the self-update applies.
- **Enums** (`TargetStatus`, `StepStatus`, `RuleField`, `ScheduleTrigger`, `StepType`) are stored as integers: append values with explicit numbers, never reorder.
- **Localisation:** every new status, rule field and setting needs English and German strings; `LocalizationTests` fails on missing keys.
- **Tests:** follow `ScheduleTests`, `PackageTests`, `TransportTests` with the file-based `TestDb`; extend `SimulatedInventory` for new sections so the simulation mode shows them.
- **Migrations:** one per item group (e.g. "deployment states", "roles", "hardware"), not one per column.
- **Documentation:** README sections *Features* and *How access works*, and SECURITY.md for roles and signed updates (an Operator can execute approved SYSTEM-level packages; an Admin is domain-admin-equivalent).
